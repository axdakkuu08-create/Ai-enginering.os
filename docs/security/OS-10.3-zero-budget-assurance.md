## 3. Preliminary code inspection — not an independent review

The following are preliminary observations from source inspection at the pinned code revision. They are not final security verdicts.

| Finding | Preliminary observation | Current disposition |
|---|---|---|
| Trusted actor identity binding | `authorizeHumanApproval` derives the subject and permission from a `HumanIdentityVerifier`, but the verifier is injected as a function argument. The repository contains no production identity-provider adapter or proven server-only composition boundary. Existing tests use mock verifiers. | INCONCLUSIVE — trust boundary not established |
| Approval authenticity and freshness | Approval decisions validate that a timestamp parses, but there is no explicit expiry/max-age policy, revocation check, cryptographic signature verification, or durable atomic single-use store in the inspected helper. | NOT ESTABLISHED — substantial controls absent |
| Decision-to-request binding | Gates bind `proposalDigest` and `baseRevision`. The inspected gate/decision contracts do not bind a complete protected-request context such as repository, installation, action, target branch, request ID, and candidate head SHA; digest computation/canonicalization is not established here. | PARTIAL — context binding incomplete |
| Audit completeness and integrity | `createSafeAuditEvent` sanitizes/redacts an event object. The inspected module does not provide durable append-only persistence, sequence enforcement, hash chaining/signatures, or tamper verification. | NOT ESTABLISHED — sanitizer is not an audit store |

The Permission Engine currently denies privileged merge/deploy capabilities with `PRIVILEGED_ACTION_BLOCKED` pending a trusted approval verifier integration. Preserve this fail-closed behavior.

## 4. Free reproducible test suite

The new characterization suite is:

`packages/core/tests/os-10.3-assurance-characterization.test.ts`

It contains four intentional expected-failure tests for the currently missing controls:

1. Approval freshness enforcement.
2. Preventing an untrusted caller from injecting the identity verifier.
3. Binding approval to repository/action/target context.
4. Tamper-evident audit sequence and integrity metadata.

The tests use Vitest already present in the repository lockfile. No new dependency is introduced. Expected failures are deliberate gap markers: they do not count as security passes. They must be converted into ordinary passing security tests only after the corresponding control exists and is verified.
