# OS-10.3 — Dedicated Neon Project Preparation

**Status: CODE-ONLY PREPARATION — NO DATABASE PROVISIONED**

## Decision

OS-10.3 will use a new, dedicated Neon project named `ai-engineering-os-103`.
It must not share either existing Neon project in the account. The prior project
creation attempt was blocked by an account-level HIPAA eligibility restriction;
no project was created. Retry only after Neon account eligibility/support has
resolved the restriction.

This document prepares the integration without creating cloud resources,
connecting to a database, generating credentials, applying migrations, or
changing production services.

## Isolation requirements

- One Neon project dedicated to OS-10.3; no cross-project database reuse.
- Project name: `ai-engineering-os-103`.
- Owner: the user's intended Neon organization, after Neon confirms eligibility.
- PostgreSQL major version: 16 or newer, subject to compatibility verification.
- Use a region selected for the deployment's actual server location and latency.
  Do not assume a region until provisioning is available.
- Do not enable HIPAA mode as a workaround for the account restriction.
- Do not enable Realtime, object storage, or unrelated Neon features.
- Keep the project private to the trusted server; never connect a mobile client
  or browser directly to the database.

## Code already prepared on the remediation branch

The remediation branch contains these database-facing contracts:

- `PostgresApprovalStore`: conditional compare-and-set transitions for one
  approval decision and one-time consumption.
- `PostgresAuditLedgerStore`: sequence-numbered SHA-256 audit ledger with a
  database head row and integrity verification.
- `SqlExecutor`: minimal parameterized SQL interface so the core package does
  not depend on a particular PostgreSQL driver.
- Approval and audit schema migration(s) are part of the remediation candidate.
  Before provisioning, the implementation owner must locate and review the
  exact migration files and compare them with the adapters; do not infer a
  migration path from this document.

These are code-level adapters, not evidence of a live database deployment.

## Planned database role separation

Provision separate PostgreSQL roles; never run the application as the project
owner or migration owner.

| Role | Intended permissions |
|---|---|
| `aios_migrator` | DDL and migration execution during controlled maintenance only |
| `aios_runtime` | Minimum required SELECT/INSERT/UPDATE permissions for approval gates; no schema ownership or DDL |
| `aios_audit_writer` | SELECT/INSERT on audit events and the narrowly scoped atomic head-advance operation; no UPDATE/DELETE on historical event rows |
| `aios_audit_reader` | Read-only access for integrity verification and export |
| project owner | Break-glass administration, not used by application services |

The exact grants and whether a narrowly scoped SECURITY DEFINER function is
needed must be reviewed against the final migration and Neon PostgreSQL
capabilities before execution. The audit writer must not be able to rewrite or
delete historical events. A database owner/superuser can still rewrite the
database, so role separation is not an independent external anchor.

## Server integration contract

The eventual server composition root must:

1. Verify Auth0 access tokens using a dedicated AIOS API audience and explicit
   client allow-list; fail closed on missing or invalid configuration.
2. Resolve the proposed GitHub action from the trusted GitHub API, never from
   client-supplied repository, branch, revision, or diff fields.
3. Evaluate policy and verify the proposal digest and base revision.
4. Re-fetch provider state immediately before the protected action.
5. Atomically consume the approval in PostgreSQL before invoking a server-owned
   GitHub App mutator.
6. Use a least-privilege GitHub App installation token scoped to the target repo.
7. Persist sanitized audit events and verify the ledger head on startup and
   before sensitive exports.
8. Fail closed if the database, Auth0 verifier, policy engine, audit store, or
   external audit anchor is unavailable.

The current `ProtectedActionGateway` is a reusable boundary, not a production
API route or a GitHub mutator. Do not label the system production-integrated
until a real composition root and provider adapter exist and are tested.

## External audit anchoring

The PostgreSQL hash chain alone is not tamper-proof against a database owner.
Before production use, define a separate independently administered anchor that
receives signed periodic checkpoints containing at least:

- project/stream identifier;
- monotonically increasing sequence number;
- latest ledger hash;
- checkpoint creation time from the trusted service;
- signature key identifier and signature.

The anchor must be outside the Neon project and outside the same administrative
trust boundary. A second table or another branch in the same Neon project does
not qualify. Do not choose or provision an anchor provider in this preparation
step.

## Provisioning and acceptance gates

Provisioning is permitted only after the Neon account restriction is resolved
and the user explicitly authorizes creation of the dedicated project.

After provisioning, the separate implementation/review task must:

- record the Neon project ID, region, PostgreSQL version, and ownership (never
  commit connection strings, passwords, or API tokens);
- create the least-privilege roles and store credentials only in the approved
  secret manager;
- apply the reviewed migration using the migrator role;
- verify schema, indexes, constraints, and grants from the database itself;
- run real concurrent approval-decision tests proving exactly one decision
  succeeds, plus replay, expiry, proposal-change, rollback, and retry tests;
- run concurrent audit append tests and verify sequence/hash continuity;
- test backup/restore and persistence across compute restart;
- test application connectivity using only the runtime role;
- independently verify external checkpoint publication and tamper detection;
- attach exact commit SHA, migration checksum, test output, and CI evidence to
  the OS-10.3 evidence record.

A green unit-test suite or mocked SQL executor is not a substitute for these
live acceptance tests.

## Explicitly out of scope until authorized

- Creating or modifying any Neon project.
- Reusing an existing Neon project.
- Generating, displaying, or storing database credentials.
- Applying SQL or running migrations.
- Connecting a production service to Neon.
- Configuring Auth0 or GitHub App production credentials.
- Deploying, merging, or changing the protected `main` branch.
